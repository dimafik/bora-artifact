# 11_potency — 회피한 공격은 실제로 무엇을 하는가

`panel2_results.json`은 각 지연 패턴이 **탐지되었는지**만 잰다. 이 폴더는 같은
패턴이 ordering service에 **무엇을 하는지**를 잰다: 표적 orderer의 리더십 획득,
커밋 처리량, 그리고 탐지기가 실제로 표적을 배제하는지.

측정 대상은 `08_predictor/r12_panel`의 white-box PGD가 만든 회피 시퀀스 그 자체다
(`extract_pgd_sequences.py`가 기록된 best_combo를 재현해 뽑았고, 재현 AUC가
기록값과 5e-4 이내로 일치함을 assert로 확인).

## 조건

7 orderer 전부에 동일한 marginal을 주고 **orderer3만 자기상관이 다르다**
(moment-matched 유지). 표적만 지연을 올리면 평균만으로 탐지되어 회피를 측정한
그 공격이 아니게 된다.

| 트랙 | 실현 자기상관 | white-box AUC |
|---|---|---|
| healthy_white | 0.026 | — |
| pgd_rho_0.0 | 0.059 | 0.003 (회피) |
| pgd_rho_0.3 | 0.316 | 0.039 (회피) |
| pgd_rho_0.6 | 0.603 | 0.332 (회피) |
| pgd_rho_0.8 | 0.799 | 0.943 (탐지) |
| attack_class_ar1 | 0.886 | — |

두 규모: `m8`(벤치마크 원본 8 ms), `m500`(곱셈 스케일 500 ms — 변동계수와
자기상관 보존).

## 핵심 결과

**폐루프에서 `bt_has_target`이 자기상관을 따라 단조 증가한다.**

```
healthy 2/40 → rho0 1/40 → rho0.3 7/40 → rho0.6 16/40 → rho0.8 24/40 → AR(1) 34/40
```

회피에 성공한 적대자(rho=0, AUC 0.003)는 40회 중 1회만 배제됐다. **배제 실패는
실제로 일어난다.** 그러나 같은 적대자는 네 지표 어디에도 흔적을 남기지 않았다.

| 지표 | 자기상관의 효과 | 변동 기준 |
|---|---|---|
| 리더십 무가드 | 우연 수준, 6조건 CI 전부 겹침 | 균등 14.3% |
| 리더십 폐루프 `Bt∋o3` | **3% → 85% 단조** | 탐지는 반응함 |
| 처리량 | -0.7% ~ -4.1%, 단조성 없음 | 변동계수 2.1% |
| 커밋 지연 p99 | -7.7% ~ +1.0%, 부호 혼재 | 변동계수 4.2% |

즉 **배제하지 못한 적대자는 배제할 필요가 없었다.**

`wins` 열은 여섯 조건 모두 우연 수준이고 신뢰구간이 겹친다. 표 2의 근거는
`bt_has_target`이지 `wins`가 아니다.

## 꼬리 지연을 잰 이유와 방법

처리량과 리더십은 분 단위 평균이고, 버스트 지연은 고전적으로 **꼬리**에 나타난다.
자기상관이 피해를 준다면 여기가 마지막 자리였다.

`--waitForEvent`가 핵심이다. 이것 없이 `peer chaincode invoke`는 orderer가
**접수한** 시점에 반환하므로 endorsement + 제출만 재고, 버스트 지연이 늘릴
것으로 예상되는 커밋 구간이 통째로 빠진다. peer의 deliver 이벤트까지 기다려야
end-to-end다.

실패는 버리지 않고 음수로 기록한다. 적게 커밋하고 빨리 끝난 조건이 좋아 보이는
착시를 막기 위해서다(실제로는 전 조건 타임아웃 0건).

결과: 지연 자체는 p50을 2118 -> 5986 ms로 **2.8배** 늘리지만, 그 위에서
자기상관의 몫은 반복 간 변동 안에 완전히 들어간다. 자기상관 최고(0.886)의 p99가
최저(0.026)보다 **372 ms 낮다**.

⚠️ 부하가 조건별로 다르다. `--waitForEvent` 때문에 워커가 지연에 묶여 500 ms
조건은 n≈212, 무지연은 n≈464다. 지연 분포 비교에는 지장이 없으나 처리량 비교로
읽으면 안 된다.

## 무효 실행과 그 이유 (반복하지 말 것)

**`closed_m8_VOID_20260822-020704` — 선출이 한 번도 일어나지 않았다.**
`leader_id()`가 로그에서 "became leader at term"을 찾는데, orderer 로그는 2초마다
`Store ActiveNodes`를 남기고 프로브가 TLS 오류를 더해 선출 기록이 tail 밖으로
밀린다. 리더를 모르면 무조건 orderer1을 pause 하도록 되어 있어, orderer1이 리더가
아니면 아무 일도 안 일어나고 새 로그도 안 생겨 **다음 반복도 같은 상태**였다.
200선출 내내 `new_leader=0`. 이를 알려주는 건 liveness 열 하나뿐이었다.

수정: 리더 미상 시 후보를 순회하며 pause. 단, `V=$(pick_victim ...)` 형태는 안 된다
— 명령 치환은 서브셸이라 카운터 증가가 부모에 전달되지 않고, `paused` 열이 1로
고정된다(2차 시도에서 실제로 그렇게 실패했다).

**같은 실행에서 임계값도 틀렸다.** 합성 healthy(`mean 8/std 3` i.i.d.)로 보정한
임계값을 라이브 RTT에 적용하면 anomaly head가 **0.9999로 포화**한다(무공격 1,099
표본 평균 0.999895). 공격이 없는데 표적이 18/40 블랙리스트됐다.

수정: **창별로 평균 8/표준편차 3 표준화 후 스코어링.** 아핀 변환이라 자기상관은
보존하고 노드 간 수준 차이(o7 0.7 ms vs 나머지 6-13 ms)만 제거한다. 라이브 무공격
평균이 0.3187 → 0.0570으로 내려가고 합성 AR(1)은 0.798을 유지한다. 보정 임계값도
0.999896 → 0.279431로 의미 있는 구간에 놓인다.

⚠️ **이 표준화는 현재 배포 파이프라인(`predictor_daemon.py`)에 없다.** 논문에는
"이렇게 돌고 있다"가 아니라 **"이 전처리가 필요하다"** 로 적어야 한다.

## 부하 생성기 (Caliper 미설치 → `loadgen.sh`)

네 개의 버그를 순차로 잡았고, 넷 다 **오류 없이 조용히 틀린 값**을 냈다.

1. 측정기가 부하 컨테이너와 수명을 공유 → 측정 직전 소멸, 종료 높이 빈 값
2. 워커 루프를 `docker exec sh -c "..."` 문자열로 전달 → 따옴표·경로 변환에 뭉개져
   시작조차 안 됨
3. `docker exec`의 `/tmp/...` 인자가 Git Bash에서 경로 변환 → 완료 감지·카운터 실패
4. 자산 키에 컨테이너 셸 PID 사용 → **실행 간 충돌**로 CreateAsset 거부.
   "클러스터가 부하를 거부했다"와 구별되지 않았다 → `RUNID`로 해결

처리량은 클라이언트가 아니라 **원장 높이 차분**으로 잰다. 이 프로젝트는 과거
Succ=0을 합의 실패로 오독해 처리량 주장을 철회한 전례가 있다.

순서 회전이 필요한 이유: 1회차 고정 순서에서 `pgd_rho_0.0`이 -12.3%로 튀었는데,
회전 4회 반복에서 -1.7%로 돌아왔다. **위치 효과**였다.

Go가 없어 일회용 `fabric-tools:2.5` 컨테이너에 Admin MSP를 마운트해 처리한다.

## 결론의 범위

네 지표 모두에서 자기상관의 효과를 **검출하지 못했다.** 이것은 무해함의 증명이
아니라 검출 실패다. 남는 한계:

- 단일 호스트 docker, orderer 7대. 호스트 간 네트워크 효과 없음
- 처리량 4회 / 지연 2회 반복 — 각각 2.1% / 4.2%보다 작은 효과는 검출 불가
- `m500`은 곱셈 스케일링으로 만든 구성물이며 벤치마크 원본은 8 ms
- 폐루프는 `m8`에서만 측정했다. 창 특징 `cc = (RTT <= 100 ms)`가 학습 전체에서
  참인데 500 ms 트랙에서는 전체에서 거짓이라, 탐지기가 본 적 없는 입력을
  받게 되고 회피와 무관한 이유로 결과가 평평해진다
